## 当前定位

这次请求被原系统归类为分享直播，未观察到进入小号秒传步骤的证据。排查重点是原网关对 provider=115share 的分流，而不是二维码展示或已有用户账号池的分配按钮。当前证据不能判定 115 的秒传接口本身失效，也不能证明普通 /play115 来源同样受影响。

普通用户 sjw 目前按此前测试约定保持未关联；这不能解释 sss 的现象，因为 sss 自己的个人 115 绑定仍然就绪。两种情况应分别处理。

## 现有插件为什么没有补上这一步

本插件现有代码管理原生独立账号、目录与用户关联，没有实现资源 upload/init。当前独立账号作用域公开了扫码、会话、目录和关联接口；已导出的 OpenAPI 及原生页面调用中没有找到“向指定 115 小号秒传文件并返回小号文件信息”的接口，也没有供插件介入每次播放的钩子。

POST /api/save_json 的当前规范明确处理 123 或光鸭 JSON 导入，不能将小号目录 ID 塞入该接口，假定它会改为 115 小号秒传。全局 115 登录接口也不能拿来替代小号授权。

115 SDK 本身提供初始化上传/秒传能力，当前容器已安装 p115client；这不等于原网关已经为分享来源调用它。已通过临时只读插件核实实际安装版本为 0.0.9.0.2，公开方法为 upload_file_init(filename, filesize, filesha1, read_range_bytes_or_hash=None, pid=0, ...)。大于等于 1 MiB 的文件需提供范围校验回调。该检查仅使用 inspect.signature / inspect.getdoc，没有读取账号、登录 115 或执行网盘请求；不能算作实际秒传通过。

新提供的插件协议明确：任务为独立子进程，不提供自定义路由或常驻播放服务，不应依赖受保护主程序的内部模块、数据库结构或 Flask 上下文。当前反代规则查询只返回规则的标识、名称、监听端口、上游、API Key、启用状态及类型，未找到已公开的“强制分享来源秒传到个人 115”开关。没有因此尝试未记录的配置写入。

## 真正需要补齐的播放处理

保持“原网关负责播放”的方案，需要原网关或其正式扩展接口完成：

1. 识别分享资源，解析已有 SHA1、大小、文件名及读取指定字节范围的源地址。
2. 根据实际 Emby 用户读取其 115 绑定，取得所选小号与接收目录。
3. 使用该小号客户端执行秒传初始化；需要二次校验时仅读取指定范围，不回退为下载整片上传。
4. 核实秒传结果及小号目标文件，保存目标文件 ID / pickcode 与源资源的映射。
5. 使用小号目标文件的 pickcode 取链，原网关返回 302；失败时如实返回业务错误。

该步骤不能用“账号已就绪”“已关联用户”或任意 115 CDN URL 替代。

## 约束下的可行范围

- 保留现有分享 STRM、原网关即时处理：需要 TgtoDrive 支持上述分享来源分支，或提供正式的账号作用域秒传接口与播放接入方式。现有插件不能通过增加一个按钮改变已经运行的网关分支。
- 纯插件单次/批次秒传验证：可以另用 115 SDK，经明确的小号授权后执行秒传、验证目标文件并返回小号链接；这属于前置任务，不会自动拦截现有分享 STRM 的播放请求，不能宣称已经修复原网关的自动播放路径。

本轮已经定位到分享直播与预期秒传的流程差异，尚未修复“分享 STRM 按播放自动秒传到小号”。未修改主程序、主号或其他用户配置。
