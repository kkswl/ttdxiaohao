# 115 小号直连管理 · 0.2.3

管理员通过独立 115 账号池为已有 Emby 用户分配小号，继续沿用 TgtoDrive 的原生绑定系统与 302 网关。插件不修改源码、不另建网关、不保存 115 Cookie。

## 当前验证范围

已在授权的 TgtoDrive v8.9.2 实例验证 Bearer 鉴权、创建测试账号记录、读取账号池和已有用户、生成二维码及二维码过期响应。用户通过原系统账号面板完成扫码和目录配置后，接口已回读 authorized=true、ready=true、status=active；正式插件也已同步显示就绪、浏览该小号目录，并重新保存当前接收目录成功。现场证据更新至 2026-11-21。

已核对原生账号页面的扫码和目录请求字段，0.2.0 内置该版本适配，不再要求普通使用者提供 JSON 字段映射。自定义 TGTO_ACCOUNT_CONTRACT 仍可覆盖适配，测试合成映射不能当作真实配置使用。

正式插件已经对另行指定的已有用户完成真实 prepare / assign / unbind，原系统回读确认关联及人数变化；解绑后该轮测试恢复为未关联，其他用户和账号记录保持原样。原先指定的邀请码用户没有被转换来源或修改绑定。

现场已完成同一影片的对照：邀请码测试用户及临时分配到独立小号的已有测试用户，均以各自登录身份获得 HEAD 302 → 115 CDN，网关记录原因为 invite_user_personal_cloud。已有用户的绑定已回读确认指向指定账号池小号，测试客户端及用户身份匹配，测试后已解绑恢复。此前的 HTTP 200 PlaybackInfo 改写是另一类请求。

**0.2.3 合并按钮的完整真实扫码仍待现场验证；资源秒传与小号取链也尚未验收。** 已有管理接口、指定用户的账号池关联及原网关 302 路径已有实际证据；HEAD 302 不能证明文件已秒传进小号，也不能确定链接来自分配的小号。多人批量、账号切换和故障恢复已有 mock 测试，真实验证范围见测试报告。

2026-11-21 对《野蛮师姐》的排查发现：邀请用户 sss 的个人 115 绑定仍就绪，原系统活动却归类为 share_direct_playback / 115share。现有插件实现账号管理，没有资源秒传或每次播放的处理入口；尚未修复分享 STRM 按播放自动秒传到小号。具体证据及原网关需要补齐的步骤见 [秒传诊断](docs/RAPID-TRANSFER-DIAGNOSIS.md)。

0.2.2 修正了扫码异常恢复：本地依赖缺失、原接口已接受但二维码图片生成失败、真正未知的写入结果分别记录；已有加密流程句柄的中断请求可查询原系统状态，不重新发起写入。旧登录仍有效时，不再据此宣告一次超时的重新登录成功。

0.2.3 对照原生用户中心，新增「检查并完成登录」：扫码并在 App 内确认后，点击一次即可检查并提交登录完成；未授权时返回当前状态。发起扫码前的影响确认保留，完成前复核账号、规则、流程和关联人数。流程对照及两类用户的区别见 docs/NATIVE-FLOW.md。

## 权限与实现边界

当前实例开发指南明确说明：Python 插件以服务账户运行，可访问服务器文件、环境变量和网络；独立进程不是权限沙箱。所有 Web 管理用户共享插件目录和数据，插件没有独立的用户权限系统。

本项目按需求通过已开放的管理员 OpenAPI 管理绑定，不修改内部数据库、不注入主进程、不另建播放服务。这些是本项目的实现约束。调用 HTTP 接口仍需运行时 Token；结果 UI 则受宿主原生组件协议约束，不能执行任意 HTML / JavaScript / CSS。

## 安装和配置

ZIP 根目录含 plugin.json、plugin.py、account_manager 模块及说明。在「实用工具 → 我的插件 → 导入插件」安装；相同插件 ID 更新保留 data_dir。

服务地址是插件进程能访问的 TgtoDrive 根地址。默认 http://127.0.0.1:12366 需要按实际容器监听端口调整；宿主映射端口不一定等于容器内端口，也可填写容器能够访问的 LAN 地址。

鉴权有两种方式：

1. 推荐在现有容器环境配置 TGTO_OPENAPI_TOKEN，表单填写变量名。环境变量不会自动注入，需要管理员通过原部署方式配置并保留 /app/db 持久卷。
2. 可在密码字段填写 Token。**密码框仅遮蔽显示；网页运行和保存设置会写入明文 settings.json，宿主也会保留明文任务参数。** OpenAPI 运行接口传 save_settings=false 可以不保存表单设置，但不能阻止宿主任务记录保存参数。

不要把真实 Token 提交到源码、安装包、截图或操作日志。环境变量优先于密码字段。TGTO_BASE_URL 仅在表单地址为空时生效。

## 操作顺序

1. 读取工作台，选择反代规则；切换规则清空临时选择、目标及旧预览。
2. 填写显示名称，预览并确认创建 115 小号。
3. 选择小号和登录设备，预览并确认发起扫码，用对应 115 小号扫码并在 App 内确认，再点「检查并完成登录」。每次检查一次；未授权时可稍后再点。旧流程或影响范围变化时，使用「预览完成登录」重新核对并确认。
4. 浏览该账号的目录，进入或选择目录，核对名称和字符串 ID 后确认。
5. 在用户表逐项加入选择，选择目标小号，核对分配变化后确认。
6. 查看逐项结果。失败项重新选择后生成新预览，结果待核实的操作先查询，不自动重放。

每批最多 30 位用户，预览有效 5 分钟，只能确认一次。改名、重新登录、改目录和删除同样先预览影响；后端仍会拒绝删除被使用的账号。

二维码在当前实例仅有效 120 秒，应在页面现场生成并立即扫码。也可在维护卡点击「打开原系统账号面板」，由该页面生成二维码、自动检查并完成登录，然后回插件点击「刷新原系统状态」。不要通过聊天中转二维码；原系统面板和插件操作的是同一个独立小号。

邀请码注册用户的个人绑定与已有用户账号池流程分别处理。本插件是管理员工具，所有宿主 Web 管理用户共享其数据，不是普通 Emby 用户的自助页面。

## 持久化和扫码保护

context["data_dir"] 中保存选择、目标、预览、脱敏操作记录及短期扫码状态。真实绑定和账号凭据以原系统为准。

原生扫码请求返回 flow_id、qr 和 expires_in。插件用 cryptography 的 AES-GCM 加密短期 flow_id，密钥由运行时 Token 与服务地址派生，并绑定规则和账号作用域；不保存派生密钥或原始 Token。Token 变化会使旧扫码上下文失效，需要重新扫码，原系统账号凭据不受影响。

流程同时关联原先确认发起扫码的预览 ID，供合并完成操作核实影响范围；不额外保存一份 115 登录凭据。升级增加此字段并保留旧上下文；旧流程没有确认引用时不会自动取得完成权限。

二维码只生成私有 PNG，结果使用 data:// 引用；不返回 qr.uid、sign、time 或原始授权内容。图片和扫码上下文按原系统有效期处理，并加上最多 5 分钟的本地保留上限。当前实例返回 120 秒。检查到过期、完成登录或删除账号时清理对应状态；每次新任务也清理过期内容，没有后台无限轮询。

写入前先保存 pending 标记。网络错误、进程中断和写后确认读取失败时查询原系统，不把未知结果当成可直接重试的失败。最终列表刷新失败仍保留逐项结果。

核实扫码请求时，只有保留了有效加密句柄并实际查询到状态，才确认流程存在或已经结束；流程存在不代表登录完成。如果开始请求的响应彻底丢失、没有句柄可查询，仍保留待核实并引导查看原系统账号面板，不靠本地等待时间推断成功或自动重试。

## 依赖与验证

使用标准库、qrcode 8.2、Pillow 12.2.0、cryptography 49.0.0；这些依赖已从当前实例运行环境核实。插件运行和导入均不 pip install。

本地开发依赖见 requirements-dev.txt，测试命令：

    .venv/Scripts/python.exe -m unittest discover -v
    python tools/validate.py
    python tools/package.py

Linux 可使用 tools/Dockerfile.test 构建独立测试镜像；开发镜像构建时安装依赖，与正式插件运行分开。0.2.3 的 Windows 和独立 Linux 环境各 74 项测试通过；本轮 Linux 复用已固定依赖的开发镜像，只读挂载当前源码，测试时禁止外网。详见 docs/TEST-REPORT.md。

原生组件只使用宿主语义 tone，跟随浅色 / 深色主题。最终宿主渲染、真实账号绑定与播放验收，以 docs/ACCEPTANCE.md 的证据为准。
